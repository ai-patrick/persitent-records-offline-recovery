2 · How the App Works

The app follows an offline-first architecture. Every record is saved locally first, then synced when the user chooses. The sync state machine makes every transition visible and auditable.

Open app→Fill form→Save → SAVED→Tap Sync→PENDING
Server OK→ACKNOWLEDGED∨Transient fail→FAILED (retry)
Permanent fail→CONFLICT (resolve)∨Lost response→Retry with same clientId

3 · Data Model & Sync States

3.1 Record Entity (Record.java)

The Record entity captures everything needed for offline-first sync:

💡 Key design. clientId is generated once on creation (UUID.randomUUID()) and never changes. This is the idempotency key — if the server receives the same clientId twice, it treats it as a duplicate and returns the original result.

3.2 Sync Status Enum (SyncStatus.java)

Explicit states eliminate ambiguity. The UI shows color-coded chips for each status.

SAVEDLocal only, not yet synced
PENDINGSync in progress
ACKNOWLEDGEDServer confirmed
FAILEDTransient error — retry safe
CONFLICTPermanent — needs resolution

4 · Local Persistence with Room

4.1 Database & DAO (AppDatabase.java, RecordDao.java)

Room provides compile-time verified SQL, reactive LiveData, and transactions.

4.2 Key DAO Queries (RecordDao.java)

⚠ Transaction boundary. The DAO methods run inside transactions when called from RecordRepository. If validation fails, an exception is thrown before any database write — no false success.

5 · Validation — No False Success

5.1 Validator (RecordValidator.java)

Validation happens before any database operation. Returns a sealed result type — either Valid with the record or Invalid with a map of field errors.

6 · Sync State Machine & Repository

6.1 State Transitions

The repository orchestrates the sync lifecycle. Every transition is explicit and auditable.

6.2 Idempotent Retry (retrySync)

Critical: the same clientId is used on retry. This prevents duplicate records if the original request actually succeeded but the response was lost.

💡 Lost response scenario. If the network times out but the server did process the request, the retry sends the same clientId. The mock server (and a real idempotent API) recognizes it and returns the original success — no duplicate created.

7 · Mock API — Controlled Test Scenarios

7.1 Mock Modes (MockApiService.java)

The mock service simulates four distinct server behaviors for testing:

✅NORMALReturns success with generated serverId
🚫UNAVAILABLEThrows IOException (transient) — safe to retry
⏰LOST_RESPONSEFirst call: throws timeout. Second call with same clientId: returns original success
⚠CONFLICTThrows 409 Conflict (permanent) — NOT safe to retry blindly
